구조도(개요·취소 플로우)가 설계의 "무엇"이라면, 이 페이지는 실측이 드러낸 "어디가 병목이고, 레버를 당기면 얼마가 바뀌나"다. 모든 수치는 AWS 리그 실측값.

1. 취소 1건의 자원 해부 — 병목은 커밋수다 [1·2막]

"190은 용량이 아니었다"·"동기 홉인 줄 알았다"의 결론: 처리량을 지배하는 건 홉 지연도 풀 크기도 아닌 커넥션 점유시간 = payment 커밋수(fsync).

커밋 6→4 = ×1.5: 이력 3커밋을 1 배치로 줄이자 rps가 정확히 6/4배(147→220). 커밋 수에 반비례하는 처리량을 정량 증명. 풀(10)은 여전히 벽이지만(pending ~189), 점유시간이 줄어 같은 벽을 더 많이 통과.

2. 발행·소비 파이프라인 — 생성 너머 [3·4막]

취소 확정 후 payment.cancelled가 order로 흐르는 경로. 발행 방식(3막)과 소비/정합성(4막)이 여기 산다.

3막(발행): 동기 send().get()가 TX3 점유에 브로커 RTT를 더함 → 제거 시 +6%(dual-write 안전값). OUTBOX 폴러는 공유 풀 굶음으로 라이브락(재발송 42만 vs 고유 1천) → 전용 DataSource 격리로 해소(PENDING→0, 1:1).
4막(소비): 컨슈머 processed_cancel_event UK가 발행 중복(at-least-once)을 흡수 → exactly-once. 실측: lag→0·DLQ델타0·e2e정합. 미러 버그가 우발적 장애주입이 되어 retry→DLQ 격리 경로까지 실증.

3. 레버 타임라인 — 당긴 것과 실측 효과 [전 막]

코드 리뷰가 못 보는 병목을 부하가 드러내고, 레버를 당긴 뒤 재측정으로 증명한 궤적.
