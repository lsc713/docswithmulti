왜 필요한가 — 실측 ③은 payment 파드가 같은 agent에서 Kafka broker와 CPU 공유 + limit 미설정이라 절대 천장이 오염됐다(상대 ×1 vs ×3만 신뢰). 아래 설계는 서비스를 EC2에 손으로 쪼개는 게 아니라, k8s의 전용 노드 풀 + Guaranteed QoS로 payment만 CPU 격리한다(스케줄러는 그대로).

1. 격리 벤치 토폴로지

파랑 payment(측정 대상, 격리) · 회색 그 외 워크로드 · 노랑 외부 DB. payment 전용 노드 풀(taint로 다른 파드 차단) + payment Guaranteed QoS(requests=limits) → CPU noisy-neighbor 제거. DB는 외부 고정(진짜 병목 후보).

payment 3벌은 각각 전용 노드 1대를 통째로(Guaranteed QoS) → CPU 경합 0. 이제 도착률을 올렸을 때 막히는 건 payment CPU가 아니라 외부 DB(공유 write)여야 한다 → ×1 vs ×3가 정말 DB 천장에서 같아지는지(replica 무효) 아니면 여전히 벌어지는지 깨끗이 판별.

3. 매니페스트/terraform 변경 (요지)

서비스를 VM에 쪼개는 게 아니라, k8s 원시로 같은 의도를 표현한다.

# terraform: payment 전용 노드 풀 3대 (taint + label)
#   k3s agent user_data: --node-taint role=payment:NoSchedule --node-label pool=payment

# payment Deployment — 전용 노드 + Guaranteed QoS
spec:
  template:
    spec:
      nodeSelector: { pool: payment }
      tolerations:
        - { key: role, value: payment, effect: NoSchedule }
      affinity:            # 노드당 1 (전용이므로 hard도 가능)
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector: { matchLabels: { app: payment } }
              topologyKey: kubernetes.io/hostname
      containers:
        - name: payment
          resources:            # requests == limits ⇒ Guaranteed QoS (CPU 격리)
            requests: { cpu: "2", memory: "2Gi" }
            limits:   { cpu: "2", memory: "2Gi" }

# risk/merchant-limit/order/kafka/redis — payment 노드에 안 가게 (taint가 자동 차단)
#   그냥 기본 워크로드 풀에 스케줄 (별도 nodeSelector 불필요)
실행은 billable — 이 설계로 재측정하려면 노드가 늘어(server1+payment3+workload3) terraform·매니페스트를 바꾸고 AWS 런을 태워야 한다. 실행 여부는 별도 결정.
