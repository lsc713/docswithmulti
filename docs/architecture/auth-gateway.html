기존 취소 코어(payment/risk/merchant-limit/order) 앞단에 인증 경계를 얹었다. 게이트웨이가 JWT를 단일 지점에서 검증하고 검증된 신원을 신뢰 헤더로 downstream에 넘기면, 각 서비스는 재검증 없이 그 헤더만 신뢰한다. 취소 로직(멱등성·TX 경계·스케줄러)은 한 줄도 바뀌지 않았다.

1. 인증 경계 토폴로지 — 기존 코어를 감싸는 게이트웨이

보라 게이트웨이(무상태) · 초록 신규 서비스 · 파랑 기존 취소 코어(불변) · 실선 = 동기 HTTP · 점선 = 기존 Kafka 흐름. 게이트웨이는 user·payment·order(order-link)만 노출(내부 2서비스 risk·merchant-limit는 미노출). payment는 결제 생성 시 order 검증(items:verify)에 X-User-Id를 포워딩한다. 브라우저(frontend)는 httpOnly 쿠키로 인증하고, 게이트웨이가 CORS·CSRF를 함께 처리한다. Bearer API 클라이언트도 병행 지원.

보안 경계: payment는 X-User-Role을 재검증 없이 신뢰한다 — 게이트웨이가 클라이언트발 X-User-*를 전 경로에서 strip 후 재설정하기 때문. 단 payment(:8080)에 직접 도달하면 헤더 위조가 가능하므로, k3s NetworkPolicy로 payment ingress를 게이트웨이 파드로만 제한하는 것이 배포 전 필수 게이트다(domain-rules.md §8-3). 없으면 인가 전체가 무력화된다.
product도 동일 클래스: POST /v1/products(상품 생성)가 신뢰헤더 X-User-Role만으로 ADMIN을 판정하므로, infra/k8s/networkpolicy/product-ingress.yaml(게이트웨이 파드 전용)이 배포 게이트에 추가된다.

2. 인증 시퀀스 — 발급(공개) → 검증(게이트) → 신뢰헤더 전달

로그인/회원가입은 공개 경로로 통과하고 응답에서 토큰을 httpOnly 쿠키로 발급(body에 토큰 없음). 이후 브라우저 요청은 쿠키를 자동 첨부하며, 상태변경(logout 등)은 X-CSRF-Token(double-submit)이 필요하다. Bearer로 오는 API 클라이언트는 CSRF 면제.

sequenceDiagram autonumber participant B as 브라우저 (frontend) participant GW as api-gateway participant U as user-service Note over B,U: 발급 — 공개 경로 (JWT 필터 없음) B->>GW: POST /v1/auth/login (email, pw) · Origin :5173 GW->>U: CORS 허용 → 라우팅 (검증 스킵) U-->>B: Set-Cookie access(httpOnly,Secure,Lax)·refresh(httpOnly,Strict)·csrf(non-httpOnly) + {result:OK} Note over B,GW: 신원 — 쿠키 인증 (GET, CSRF 면제) B->>GW: GET /v1/auth/me (쿠키 자동 첨부) GW->>GW: 쿠키 access_token → HS256 검증 → 신원 추출 GW->>U: /me + 신뢰헤더 X-User-Id (재검증 없이) U-->>B: {userId, email, name, role} Note over B,U: 상태변경 — CSRF double-submit B->>GW: POST /v1/auth/logout + X-CSRF-Token (= csrf 쿠키) alt 쿠키 csrf == 헤더 & 유효 JWT GW->>U: logout (신뢰) U-->>B: 200 + 쿠키 만료(Max-Age=0) else CSRF 불일치 · 누락 GW-->>B: 403 CSRF_TOKEN_INVALID else 무효 · 만료 JWT GW-->>B: 401 end

쿠키 속성: access=HttpOnly·Secure·SameSite=Lax(세션), refresh=HttpOnly·Strict·Path=/v1/auth/refresh, csrf=non-HttpOnly(JS가 읽어 헤더로 재제출). /v1/auth/refresh는 refresh 쿠키를 읽어 새 access 쿠키만 회전. logout: refresh DB 하드 DELETE + 쿠키 만료(Max-Age=0). CSRF: 상태변경 요청은 쿠키 csrf == 헤더 X-CSRF-Token 검증(Bearer 요청은 면제). CORS: 출처 화이트리스트(localhost:5173) + credentials. JWT_SECRET은 user-service·gateway 공유(비-local 미주입 시 fail-fast).

ADMIN 역할관리: role은 서버만 결정한다(클라 입력 무시, D-P1-2). 최초 ADMIN은 app.admin.bootstrap-emails(env)에 등재된 이메일이 signup 시 자동 승격 — 부트스트랩. 이후 변경은 PATCH /v1/admin/users/{id}/role(범용 승격/강등)로, 게이트웨이 /v1/admin/** 인증 라우트를 거쳐 user-service가 hasRole(ADMIN)로 인가한다(비-ADMIN 403). role은 로그인 시점 JWT에 임베드되므로 승격 후 재로그인 시 반영(기존 토큰 무효화는 별도).

어드민 콘솔(v1.0): 별도 엔트리 admin.html(react-router)이 이 인증 경계 위에서 동작한다. 진입 시 GET /v1/auth/me로 역할을 확인해 비-ADMIN은 로그인으로 리다이렉트(프론트 가드), 실제 인가는 항상 서버가 판정. ADMIN 전용 기능 3종이 게이트웨이 인증 라우트를 거친다 — 회원관리 GET /v1/admin/users·PATCH …/role(user-service hasRole(ADMIN)), 상품 이미지 write, 상품 생성 POST /v1/products. 뒤 둘은 product-service가 주입된 X-User-Role=ADMIN을 재검증(비-ADMIN 403). 게이트웨이는 기존 POST /v1/products를 미노출(404)했으나 어드민 상품 등록을 위해 ADMIN 인증 라우트로 노출했다(client-facing 경계 확장).

4. payment 인가 판정 — role 매트릭스

신뢰 헤더의 role만으로 판정. payment는 user와 미연결이라 소유권은 merchant_id로 근사한다.

ADMIN은 전체 취소 허용(payment 조회 불요). MERCHANT는 대상 payment.merchantId를 read-only 1회 조회해 본인 가맹점만 허용. USER는 대상 payment.userId를 read-only 1회 조회해 본인 결제만 자가취소 허용. X-User-Id는 USER 인가 판정용 및 감사 로깅용. 판정 로직은 domain 순수 POJO(CancelAuthorizer).
