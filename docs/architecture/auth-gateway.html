기존 취소 코어(payment/risk/merchant-limit/order) 앞단에 인증 경계를 얹었다. 게이트웨이가 JWT를 단일 지점에서 검증하고 검증된 신원을 신뢰 헤더로 downstream에 넘기면, 각 서비스는 재검증 없이 그 헤더만 신뢰한다. 취소 로직(멱등성·TX 경계·스케줄러)은 한 줄도 바뀌지 않았다.

1. 인증 경계 토폴로지 — 기존 코어를 감싸는 게이트웨이

보안 경계: payment는 X-User-Role을 재검증 없이 신뢰한다 — 게이트웨이가 클라이언트발 X-User-*를 전 경로에서 strip 후 재설정하기 때문. 단 payment(:8080)에 직접 도달하면 헤더 위조가 가능하므로, k3s NetworkPolicy로 payment ingress를 게이트웨이 파드로만 제한하는 것이 배포 전 필수 게이트다(domain-rules.md §8-3). 없으면 인가 전체가 무력화된다.

2. 인증 시퀀스 — 발급(공개) → 검증(게이트) → 신뢰헤더 전달

로그인은 토큰 없이 통과(공개 경로), 취소는 Bearer JWT 필요. 게이트웨이가 검증·strip·주입을 한 곳에서 처리한다.

sequenceDiagram autonumber participant C as 클라이언트 participant GW as api-gateway participant U as user-service participant P as payment (인가 pre-check) Note over C,U: 발급 — 공개 경로 (JWT 필터 없음) C->>GW: POST /v1/auth/login (email, pw) GW->>U: 라우팅 (검증 스킵) U-->>C: access(JWT HS256, 1h) + refresh(opaque, 7d) Note over C,P: 취소 — 인증 경로 C->>GW: POST /v1/payments/{key}/cancel + Bearer GW->>GW: 클라 X-User-* strip alt 유효 JWT GW->>GW: HS256 검증 → 신원 추출 GW->>P: 취소 + X-User-Id/Role/Merchant-Id (신뢰) P->>P: 인가 pre-check (role) P-->>C: 취소 진행 (기존 플로우) / 403 else 무효·만료·누락 GW-->>C: 401 (downstream 미도달) end

refresh 미회전: access 만료 시 /v1/auth/refresh로 새 access만 발급(refresh 재사용). logout: refresh를 DB에서 하드 DELETE → 이후 갱신 불가. JWT_SECRET은 user-service·gateway가 공유(env 주입, 비-local 미주입 시 fail-fast).

3. 기존 취소 코어와의 연결 — 인증 경계가 앞단에 얹힘

왜 pre-check인가: 인가는 CancelController에서 cancelPaymentUseCase.cancel() 호출 이전에 던진다. 취소 코어(CancelPaymentService·CancelTxWriter·스케줄러 3종·outbox)는 byte-for-byte 무변경 — git diff(merge-base 기준)로 코어 파일 부재를 CI 게이트로 강제한다.

4. payment 인가 판정 — role 매트릭스

신뢰 헤더의 role만으로 판정. payment는 user와 미연결이라 소유권은 merchant_id로 근사한다.

ADMIN은 전체 취소 허용(payment 조회 불요). MERCHANT는 대상 payment.merchantId를 read-only 1회 조회해 본인 가맹점만 허용. X-User-Id는 인가에 미사용(감사 로깅용). 판정 로직은 domain 순수 POJO(CancelAuthorizer).
