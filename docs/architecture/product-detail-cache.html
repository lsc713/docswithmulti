상품 상세 조회는 캐시를 우선 사용하되, 가격과 재고의 최종 정합성은 DB 쓰기 경계가 책임진다. 인기 상품은 refresh-ahead, 나머지는 cache-aside로 운영한다.

상태 구분: fresh는 TTL 안의 정상 응답, stale은 soft TTL 이후 hard TTL 전의 응답, miss/expired는 캐시가 없거나 hard TTL이 지난 상태다.

인기 판정은 운영 지표로 조정한다. 캐시 용량과 refresh 비용이 커지면 상위 비율을 낮추고, miss율이 높으면 대상군을 확대한다.

3. 캐시 스탬피드 방지

sequenceDiagram participant U as 동시 요청 participant R as Redis participant L as Single-flight participant D as MySQL U->>R: MISS / EXPIRED R-->>U: 키별 락 획득 시도 L->>D: 선두 요청 1건만 상세 조회 D-->>L: 결과 L->>R: 값 저장 + TTL jitter L-->>U: 결과 반환 U->>R: 후속 요청은 캐시 재조회
실패 시: 락 획득 실패나 Redis 장애는 DB fallback으로 응답한다. 단, 예약·재고 차감의 성공 여부를 캐시 값으로 판단하지 않는다.

fresh/stale는 응답 신선도 상태이지 재고 예약 가능 여부가 아니다. 재고 차감은 항상 DB 조건부 UPDATE 결과를 기준으로 처리한다.

5. 적용 범위와 관측 항목

  • 키: product:detail:{productId}; 값: 상세 응답 envelope.
  • 측정: cache hit/miss/stale 비율, refresh 성공률, single-flight 대기시간, DB fallback 비율, 상세 API p95.
  • 무효화: 상품·가격·재고 변경 경로에서 같은 상품 키를 제거한다.
  • 부하 실측 계측: LOADTEST_QUERYCOUNT_ENABLED=true(요청당 SQL 수 db.queries.per_request) — 기준 처리량 측정 시에는 오버헤드 제외를 위해 끈다.
  • Micrometer 타이머: product.detail.cache.read(Redis 조회+역직렬화), product.detail.response.assembly(DTO 조립).

설계에 남는 결론

  • 캐시가 병목을 옮겼다. 1·2단계의 첫 포화는 MySQL이었으나, read-through 도입 후 MySQL CPU는 59.9%로 내려가고 포화 지점이 product JVM으로 이동했다. 쿼리 최적화(SQL 8→6)만으로는 +6.61%에 그쳤다.
  • 로컬 Redis로는 수평 확장할 수 없다. 인스턴스별 캐시는 stale 응답·hit율 하락·인스턴스 간 stampede 미방지를 부른다. 공용 Redis로 키·락·무효화를 공유한 뒤 확장해 4,143 RPS를 얻었다(§3의 single-flight 락이 공용 Redis 전제).
  • 쓰기는 캐시를 우회한다. reserve/release는 §4대로 MySQL 조건부 UPDATE가 권위이므로, 적중률을 올려도 혼합 워크로드의 상한은 공용 MySQL CPU가 정한다(읽기 25~50 VU 사이 포화 시작).
  • 인스턴스 증설은 이 상한을 넘지 못한다. product 2→4대에서도 ~7.8k RPS가 유지됐다. 다음 조치는 노드 추가가 아니라 느린 쿼리·트랜잭션 범위·행 잠금 경합 검토다.
