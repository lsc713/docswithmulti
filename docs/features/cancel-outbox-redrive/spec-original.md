# DEAD 취소 아웃박스 통제 재발행 — 초기 아이디어

## 배경

결제 취소와 재고 복원 E2E를 검증하는 과정에서 `cancel_event_outbox`에 `DEAD` 상태로 남아 있는 이벤트 2건을 확인했다. 두 결제는 이미 `CANCELLED`였지만 주문은 `DELIVERY_WAITING`, 주문상품은 `ACTIVE`, 재고 예약은 `RESERVED`였다.

이는 결제 취소 자체가 실패한 것이 아니라, 결제 취소 후 `payment.cancelled` 이벤트가 Kafka에 발행되지 않아 주문 취소와 재고 복원이 실행되지 않은 상태다.

## 초기 요구

- `DEAD` 이벤트를 무조건 삭제하거나 무조건 재발행하지 않는다.
- 결제, 주문, 재고의 현재 상태를 확인해 재발행 필요 여부를 판단한다.
- 주문이나 재고 중 하나라도 미처리라면 재발행 대상으로 본다.
- 주문과 재고가 이미 모두 처리됐다면 재발행하지 않고 해결된 상태로 종결한다.
- 누가 어떤 사유로 재발행했는지 기록한다.
- 재발행 성공은 Kafka 전송 성공이 아니라 주문과 재고의 최종 수렴으로 판단한다.
- 기능은 단계적으로 개발한다. 첫 단계는 운영자용 내부 API/CLI이며 관리자 화면과 자동 복구는 후속 단계로 둔다.

## 초기 상태 개념

```text
DEAD
  ├─ 재발행 필요
  │    → REDRIVE_REQUESTED
  │    → REDRIVING
  │    → RESOLVED
  │
  └─ 이미 주문·재고 처리됨
       → RESOLVED_ALREADY_APPLIED
```

원본 `cancel_event_outbox`의 `DEAD` 기록은 보존하고, 별도 재발행 이력에서 진행 상태와 결과를 관리한다.
