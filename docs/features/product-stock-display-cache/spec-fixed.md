# 상품 상세 재고 표시·캐시 요구사항

## 목적

상품 상세의 재고 표시는 빠르게 제공하되, 구매 가능 여부는 항상 재고 원본 기준으로 판정한다. 재고 변경마다 상품 상세 전체 캐시를 무효화하지 않고, 품절 상태를 분리해 갱신한다.

## 확정 요구사항

### 사용자와 최소 흐름

- 1차 사용자는 상품 상세에서 재고·품절 상태를 보고 구매를 시도하는 구매자다.
- 재고가 있으면 상세에 수량과 구매 가능 상태를 표시한다.
- 예약으로 재고가 0이 되면 품절 상태가 빠르게 반영된다.
- stale 화면에서 구매를 시도해도 `reserve`가 MySQL 기준으로 재검증해 oversell을 막는다.

### 데이터와 정합성

- 상품 본문과 가격은 기존 Product detail Redis 캐시를 사용한다.
- 가용 재고의 권한 있는 원본은 MySQL `product_stock`이다.
- 표시용 품절 상태는 Redis에 상품별로 분리한다. 짧은 TTL을 사용하고 재고가 0↔양수로 전환되면 즉시 갱신한다.
- `POST /v1/stock/reserve`는 기존 조건부 차감과 `paymentKey` 멱등 규칙을 유지한다.
- 재고는 0 이상 정수이며, 동일 예약 키 재시도는 기존 결과를 재사용한다.
- Redis 재고 상태가 없거나 만료되면 MySQL에서 읽어 다시 채운다.

### 오류 처리

- Redis 재고 상태 조회 실패 시 MySQL로 fallback한다.
- Redis와 MySQL 모두 실패하면 상품 상세는 5xx를 반환한다.
- 재고 부족은 기존 비즈니스 오류를 유지하고 프론트는 “방금 품절됨”으로 안내한다.
- 캐시 갱신 실패는 이미 성공한 예약을 롤백하지 않으며 TTL 만료 뒤 재조회로 회복한다.

### UI 범위

- 기존 상품 상세 재고 영역에서 `구매 가능` 또는 `품절`을 표시한다.
- 예약이 재고 부족으로 실패하면 안내 문구를 표시하고 최신 상태를 다시 조회한다.
- 실시간 수량 카운터, WebSocket/SSE, 판매자 재고 관리 UI는 이번 범위에서 제외한다.

### 성능·관측

- 혼합 부하는 상세 조회와 예약/해제를 함께 실행한다.
- ramp는 `500 → 750 → 1,000 → 1,250 VU`, 각 3분으로 실행한다.
- 각 구간에서 k6·Product 각 인스턴스·MySQL·Redis의 CPU/메모리, RPS, 읽기·쓰기 p95/p99, 오류율, MySQL `threads_running`, Redis cache hit/miss를 기록한다.
- 최초 포화 주체를 구간별 지표로 판정한다.

### 향후 확장과 제외 범위

- 다음 단계에서 실제 트래픽 비율로 읽기·쓰기 비율과 Product/k6 수평 확장을 판단한다.
- 이번에는 다중 리전 재고, 실시간 푸시, 판매자 UI를 구현하지 않는다.

## 용어 정의

| 용어 | 정의 |
|---|---|
| 상품 본문 캐시 | 이름·이미지·설명·가격을 담는 기존 Product detail Redis 캐시 |
| 가용 재고 | `product_stock.available_qty`의 권한 있는 수량 |
| 품절 상태 | 가용 재고가 0인지 나타내는 상품별 표시 상태 |
| reserve | MySQL 조건부 차감으로 실제 구매 가능 여부를 판정하는 재고 예약 API |
| stale 표시 | 캐시에 남아 있는 과거 재고 정보로 인한 일시적 UI 불일치 |
| 혼합 ramp | 읽기·쓰기 요청을 함께 실행하며 VU를 단계적으로 높이는 부하 방식 |
