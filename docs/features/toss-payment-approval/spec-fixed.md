# 토스 테스트 결제 승인 — 확정 요구사항

## 1. 개요

현재 체크아웃은 주문을 만든 뒤 payment-service가 자체 `paymentKey`를 생성하고 결제를 즉시
`COMPLETED`로 저장한다. 토스페이먼츠 결제창이나 승인 API는 호출하지 않는다.

이번 기능은 일반 구매자가 토스페이먼츠 테스트 결제창에서 인증하고, payment-service가
서버에서 승인한 경우에만 결제를 완료하도록 바꾼다. 판매자·관리자 화면, 승인 후 취소 정책,
정산 정책은 기존 동작과 계약을 유지한다.

## 2. Primary user

- 주 사용자: 로그인한 일반 구매자
- 구매자는 기존 체크아웃에서 주문 금액을 확인하고 토스 테스트 결제를 진행한다.
- 판매자와 관리자는 이번 기능의 새 화면이나 새 작업 흐름을 사용하지 않는다.

## 3. 최소 동작 시나리오

### 3.1 결제 성공

1. 구매자가 주문을 생성하고 결제를 시작한다.
2. 서버가 결제 시도와 서버 계산 금액을 저장하고 재고를 예약한다.
3. 구매자가 토스 결제창에서 인증한다.
4. 성공 리다이렉트 후 서버가 저장 금액, 주문 소유자와 요청 값을 검증한다.
5. 서버가 토스 승인 API를 호출한다.
6. 승인에 성공한 결제만 `COMPLETED`가 되며 기존 결제 완료 이벤트와 후속 흐름을 실행한다.

### 3.2 구매자 취소

1. 구매자가 토스 결제창을 닫거나 결제를 취소한다.
2. 서버는 토스 승인 API를 호출하지 않는다.
3. 결제 시도는 확정 실패로 종료되고 재고 예약은 해제된다.
4. 주문은 배송·정산 대상이 되지 않으며 구매자는 체크아웃에서 다시 결제할 수 있다.

### 3.3 승인 실패 또는 결과 불명

1. 금액 불일치나 토스의 명시적 거절은 확정 실패로 처리한다.
2. 승인 API 타임아웃이나 연결 단절은 결과 불명으로 처리한다.
3. 결과 불명 결제는 `PENDING`과 재고 예약을 유지하고 토스 조회 API로 최종 상태를 확인한다.
4. 중복 요청이나 복구 조회가 발생해도 승인, 재고 차감, 완료 이벤트는 각각 한 번만 반영된다.

## 4. 데이터와 상태

### 4.1 식별자

- `orderId`: 기존 order-service의 숫자 주문 식별자
- `paymentRequestId`: 우리 시스템이 결제 시도마다 발급하는 식별자. 토스 결제 요청의
  `orderId`, 재고 예약과 결제 승인 멱등 기준으로 사용한다.
- `pgPaymentKey`: 토스가 결제 인증 성공 후 발급하는 결제 키. 승인 호출 전에 결제 시도에
  연결해 저장하며 기존 외부 결제 API에서 의미하던 `paymentKey`는 이 값을 뜻한다.

`paymentRequestId`와 `pgPaymentKey`는 서로 다른 의미이며 같은 필드에 저장하지 않는다.

### 4.2 상태

- 결제 승인 전과 승인 결과 불명: `PENDING`
- 토스 승인 성공: `COMPLETED`
- 사용자 취소, 명시적 거절, 검증 실패: `FAILED`
- 기존 승인 후 상태인 `PARTIAL_CANCELLED`, `CANCELLED`, `CANCEL_FAILED`와 관련 정책은 유지한다.

### 4.3 무결성 규칙

- 주문 하나에는 활성 `PENDING` 결제 시도를 하나만 허용한다.
- 실패·취소·만료된 결제를 재시도할 때는 새 `paymentRequestId`를 발급한다.
- 동일 `paymentRequestId`의 승인 요청은 중복·동시 호출되어도 한 번만 효과를 낸다.
- 동일 `pgPaymentKey`는 하나의 결제 시도에만 연결한다.
- 승인 유효시간이 지나도록 인증·승인되지 않은 `PENDING`은 만료 실패로 수렴시키고 재고를
  해제한다. 결과 불명인 승인 요청은 조회로 승인 여부를 먼저 확정한 뒤 처리한다.
- 결제 완료 이벤트는 토스 승인 성공과 결제 `COMPLETED` 저장 이후에만 발행한다.

## 5. 검증과 경계 조건

- 결제 금액은 주문 항목을 기준으로 서버가 다시 계산한다.
- 브라우저가 보낸 금액과 성공 URL의 금액은 승인 금액의 기준으로 신뢰하지 않는다.
- 저장된 서버 금액과 토스 인증 결과의 `orderId`, `amount`가 일치해야 승인 API를 호출한다.
- 결제 금액은 1원 이상의 정수 KRW만 허용한다.
- 로그인 사용자에게 소유권이 없는 주문은 승인할 수 없다.
- 지원 결제 유형은 `NORMAL`만 허용한다.
- 비밀 키는 payment-service 환경변수 또는 Secret으로만 공급하고 프런트엔드와 저장소에
  노출하지 않는다.

## 6. 오류 처리

- 사용자 취소와 토스의 명시적 거절은 `FAILED`로 기록하고 재고 예약을 해제한다.
- 금액·주문 식별자·소유권 불일치는 토스 승인 호출 전에 거절하고 보안 로그를 남긴다.
- 승인 API 타임아웃과 연결 단절은 즉시 실패로 단정하지 않고 `PENDING`을 유지한다.
- 결과 불명 건은 토스 결제 조회 결과에 따라 `COMPLETED` 또는 `FAILED`로 수렴시킨다.
- 결과 확인 중에는 재고 예약을 유지한다.
- 구매자 화면에는 정제된 오류 코드와 재시도 동작만 제공하고 PG 원문 응답, 비밀 키,
  내부 장애 세부정보는 노출하지 않는다.

## 7. UI 일관성

- 기존 `Checkout`의 상품·금액 요약과 결제 버튼을 유지한다.
- 결제 버튼에서 토스 V2 결제창 오버레이를 실행한다.
- 승인 성공 후 기존 `OrderSuccess` 형태로 결제 키, 금액과 완료 상태를 보여준다.
- 실패 리다이렉트는 기존 체크아웃 스타일로 실패 사유와 `다시 결제` 동작을 제공한다.
- 별도 전역 상태관리 도구나 새 UI 컴포넌트 라이브러리는 추가하지 않는다.

## 8. 성능과 운영 제약

- 인증 성공 리다이렉트 직후 승인을 요청해 토스의 승인 유효시간 안에 처리한다.
- PG HTTP 연결 및 응답 타임아웃은 배포 설정으로 조정할 수 있어야 한다.
- 결과 불명인 `PENDING` 결제만 제한된 배치로 조회하며 정상 결제에 추가 폴링을 붙이지 않는다.
- 주문 항목 수와 일반 API 응답시간은 기존 주문 API 정책을 유지한다.
- 첫 버전을 위해 캐시, 별도 메시지 큐 또는 독립 복구 서비스를 추가하지 않는다.

## 9. 향후 확장성과 이번 범위 제외

### 이번에 지원

- 토스페이먼츠 V2 결제창
- 테스트 키를 이용한 `NORMAL` 일회성 즉시 승인 결제
- 서버 승인 및 결과 불명 결제의 조회 복구

### 이번에 제외

- 가상계좌 입금 웹훅과 비동기 승인 대기 결제수단
- 자동결제와 빌링키
- 복수 PG 라우팅과 장애 시 다른 PG로 전환
- 쿠폰, 포인트, 분할 결제
- 판매자·관리자 화면 변경
- 기존 승인 후 취소 정책과 정산 계산·이벤트 계약 변경

토스 승인과 조회 호출은 애플리케이션 로직에서 교체 가능한 외부 경계로 격리한다. 구체적인
인터페이스와 트랜잭션 구성은 다음 PRD의 아키텍처 대안 비교에서 결정한다.

## 10. 용어 정의

| 용어 | 정의 |
|---|---|
| 주문 | 구매 항목과 구매자를 보관하는 order-service의 레코드 |
| 결제 시도 | 한 주문에 대해 토스 인증과 승인을 한 번 시도하는 단위 |
| 결제 인증 | 구매자가 토스 결제창에서 결제수단 인증을 마치고 `paymentKey`를 받는 단계 |
| 결제 승인 | payment-service가 토스 서버 API를 호출해 실제 결제를 확정하는 단계 |
| 결과 불명 | 승인 요청의 응답을 받지 못해 토스에서 승인됐는지 단정할 수 없는 상태 |
| 재고 예약 | 결제가 확정되거나 실패할 때까지 해당 수량을 다른 구매가 사용할 수 없게 잡아두는 것 |
| `paymentRequestId` | 우리 시스템의 결제 시도 식별자이자 토스 요청의 `orderId` |
| `pgPaymentKey` | 토스가 인증 성공 후 발급하는 외부 결제 식별자 |
| `paymentKey` | 기존 외부 API 호환 명칭. 토스 연동 후에는 `pgPaymentKey`를 의미 |

## 11. 공식 계약 근거

- 토스 V2 결제창은 인증 성공 URL로 `paymentKey`, `orderId`, `amount`를 전달한다.
- 서버는 최초 저장한 금액과 인증 결과를 검증한 뒤 `POST /v1/payments/confirm`을 호출한다.
- 승인 API에는 토스 시크릿 키를 사용하며 클라이언트 키와 분리한다.
- 승인 응답이 불명확하면 즉시 실패로 단정하지 않고 결제 조회 API로 상태를 확인한다.
