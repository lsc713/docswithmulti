# Mock PG 후속 개발 설계

## 목표

`feat/mock-pg` 브랜치에서 외부 PG 없이 핵심 구매 흐름을 반복 검증할 수 있게 하고, 사용자 로그아웃 동작과 관리자 카테고리 생성 기능을 완성한다.

## 범위와 순서

1. Mock PG 전체 E2E 안전망
2. 일반 사용자 로그아웃 후 첫 상품 화면 복귀
3. 관리자 카테고리 생성

상품 수정·삭제, 카테고리 수정·삭제·정렬, Mock 실패/지연 제어 화면은 이번 범위에서 제외한다.

## 검토한 접근

### A. 실제 서비스 전체 흐름 E2E — 채택

`local,mock-pg` payment-service와 `VITE_PAYMENT_PROVIDER=mock` 프론트를 대상으로 Playwright가 구매자와 관리자를 각각 로그인시킨다. 주문, Mock 결제 승인, 취소 요청, 관리자 승인, 구매자 취소 상태까지 실제 API와 DB를 통과시킨다. 초기 실행 비용은 있지만 이후 결제·재고·취소 회귀를 한 테스트가 잡는다.

### B. 프론트 API 스텁 E2E

빠르지만 백엔드 Mock PG 프로필, 결제 저장, 취소 승인과 재고 복구를 검증하지 못하므로 채택하지 않는다.

### C. 백엔드 통합 테스트만 추가

PG 포트 선택은 검증할 수 있지만 브라우저 콜백과 사용자·관리자 화면 연결을 놓치므로 보조 테스트로만 사용한다.

## 1. Mock PG 전체 E2E

새 Playwright 시나리오는 다음 계약을 검증한다.

1. 구매자가 상품을 선택하고 주문서를 거쳐 `결제하기`를 누른다.
2. 브라우저는 `js.tosspayments.com` 및 `*.tosspayments.com`으로 요청하지 않는다.
3. Mock 성공 콜백이 기존 `/payment/success` 경로와 confirm API를 사용해 결제를 `COMPLETED`로 만든다.
4. 구매자가 주문내역에서 취소를 요청하면 `취소 요청됨` 상태가 표시된다.
5. 별도 관리자 브라우저 컨텍스트가 `/admin/cancel-requests`에서 동일 결제키를 찾아 승인한다.
6. 구매자 주문내역을 다시 조회하면 결제가 `취소됨`으로 표시된다.

기존 카탈로그 설정과 로그인 헬퍼를 재사용한다. 테스트는 환경변수 `VITE_PAYMENT_PROVIDER=mock`이 없는 실행에서는 명시적으로 skip하여 실제 Toss E2E와 계약을 섞지 않는다.

백엔드는 `mock-pg` 프로필에서 정확히 하나의 `TossPaymentPort`가 활성화되는지 작은 컨텍스트 테스트를 남긴다. 기존 `MockPgCancelClient` 테스트는 취소 포트의 안전망으로 유지한다.

## 2. 로그아웃 후 첫 화면 복귀

성공한 로그아웃은 인증 정보, 장바구니, 주문 진행 세션을 지우고 브라우저 주소를 `/`로 replace한 뒤 홈 상품 목록을 표시한다. 뒤로가기로 인증이 필요한 주문·결제 화면이 다시 나타나지 않아야 한다.

로그아웃 API가 실패하면 현재와 동일하게 사용자와 화면 상태를 유지한다. 성공과 실패를 기존 `order-flow.spec.js`에서 각각 검증한다.

구현은 `App.jsx`의 기존 로그아웃 성공 콜백에서 `openStoreView({ name: 'home' }, true)`를 호출하는 최소 변경으로 제한한다.

## 3. 관리자 카테고리 생성

### API와 권한

기존 `POST /v1/categories` 도메인 기능을 재사용한다. 현재 게이트웨이는 GET 카테고리만 공개 라우팅하므로 다음 두 보안 경계를 보완한다.

- api-gateway의 인증 product write 라우트에 정확 경로 `POST /v1/categories`를 추가한다.
- product-service `CategoryController`가 게이트웨이의 `X-User-Role`을 받아 `ADMIN`이 아니면 403을 반환한다.

일반 사용자와 미인증 사용자는 카테고리를 만들 수 없어야 한다. 기존 공개 `GET /v1/categories`는 그대로 유지한다.

### 관리자 UI

관리자 사이드바에 `카테고리 관리`를 추가하고 `/admin/categories`를 `ADMIN` 전용으로 보호한다. 한 화면에서 현재 3단계 트리를 보여주고 아래 입력으로 생성한다.

- 상위 카테고리 없음: 대분류 생성
- 대분류 선택: 중분류 생성
- 중분류 선택: 소분류 생성
- 소분류는 상위 카테고리로 선택할 수 없음

생성 성공 후 트리를 다시 불러오고 새 카테고리를 표시한다. 빈 이름, 중복 이름, 3단계 초과 오류는 서버 메시지를 화면에 표시한다. API 클라이언트에는 `createCategory({ parentId, name })` 한 메서드만 추가한다.

관리자 E2E는 대분류 → 중분류 → 소분류를 순서대로 생성하고 상품 등록 화면의 카테고리 선택 목록에서 새 소분류가 보이는지 검증한다.

## 오류 처리

- Mock 결제 confirm 실패는 기존 결제 결과 폴링과 실패 화면 계약을 사용한다.
- 로그아웃 실패는 사용자 상태를 제거하지 않는다.
- 카테고리 생성 400/403/409 응답은 공통 API 오류 변환을 통해 관리자 화면에 표시한다.
- 카테고리 생성 버튼은 요청 중 중복 제출되지 않도록 비활성화한다.

## 테스트

- payment-service: Mock PG 프로필 빈 선택 테스트와 전체 테스트
- api-gateway: `POST /v1/categories` 인증 라우팅 테스트
- product-service: ADMIN 성공, USER 403 컨트롤러 테스트
- frontend unit: 필요한 순수 상태 변환만 테스트
- Playwright: Mock 결제→취소 승인 전체 흐름, 로그아웃 홈 복귀, 관리자 3단계 카테고리 생성
- 최종 검증: 관련 Gradle 테스트, `npm run test:unit`, `npm run build`, 대상 Playwright 시나리오

## 완료 조건

- Mock 모드 전체 구매·취소 승인 E2E가 외부 Toss 요청 없이 통과한다.
- 성공한 일반 사용자 로그아웃은 항상 `/`의 첫 상품 화면으로 복귀한다.
- ADMIN은 3단계 카테고리를 생성할 수 있고 USER는 API로 우회 생성할 수 없다.
- 기존 실제 Toss 코드 경로와 공개 카테고리 조회가 회귀하지 않는다.
