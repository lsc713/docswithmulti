<objective>
전역 속성 사전(attribute/attribute_value)을 세우고, 상품 등록 시 변형 속성을 선언해 SKU를 변형값의 완전·유일 조합으로 정의하며, 상세 조회가 그 조합을 구조화(variantOptions + per-SKU variant)해 노출한다. Flyway V8만 추가하고 기존 재고·취소·브라우징 경로는 건드리지 않는다(순수 카탈로그 추가).

Purpose: option_summary 자유문자열을 구조화 변형 모델로 정규화하는 수직 슬라이스의 코어. Phase 2(서술 속성)가 이 위에 얹힌다.
Output: V8 마이그레이션 · Attribute 도메인/서비스/컨트롤러 · CatalogService·ProductQueryService·SeedRequest·ProductDetailResponse 확장 · 3개 Testcontainers 통합테스트.
</objective>

<design_decisions>
설계 §10 열린 질문 확정 (권위 spec: docs/superpowers/specs/2026-08-03-product-attribute-variant-design.md):

- **조합 유일성 = 앱 레벨 검증만 (combo_hash 컬럼·UK 없음).** 정렬된 variant value id 집합 비교로 상품 내 SKU 조합 중복을 검출한다. 근거: 이 Phase에서 SKU는 오직 상품 등록(seed) 한 번의 요청·한 TX에서만 생성된다 — 기존 상품에 SKU를 추가하는 엔드포인트가 없어 동시 쓰기로 인한 TOCTOU가 성립하지 않는다. sku_attribute_value PK(sku_id, attribute_value_id)가 행 중복을 막고, 앱 집합 비교가 조합 중복을 막는다. 상한(ponytail): "add-SKU-to-existing-product" 엔드포인트가 생기면 그때 sku에 combo_hash STORED 컬럼 + UK(product_id, combo_hash)를 도입한다 (category.parent_key 트릭과 동형).
- **인라인 속성 생성 불허.** 속성/값은 POST /v1/attributes(/{id}/values)로 먼저 생성하고 상품 등록은 id만 참조한다 (spec §5 권고 유지).
- **GET /v1/attributes 페이징 없음.** 사전 소규모 가정 → 전체 반환.
- **Phase 1은 변형만 사용/검증.** V8은 5 테이블(product_descriptive_value 포함)을 한 번에 만들되 product_descriptive_value·서술 경로는 Phase 2. SeedRequest.attributes[].isVariant는 저장하되 Phase 1 검증/노출은 is_variant=true만. descriptiveValueIds 필드는 Phase 2에서 추가.
</design_decisions>
