<objective>
Wire settlement-service's three NEW module capabilities (Redisson distributed-lock scheduler, cross-module HTTP pull, operation alerting) and deliver the reconcile→finalize vertical slice end-to-end: a week-closed OPEN ledger → scheduler acquires the Redisson lock → HTTP-pulls payment's settlement query → back-fills event-lost SALE/CANCEL lines through the existing record() path (event_id UK dedup) → recomputes gross/cancel from Σlines → computes fee/vat/net → transitions OPEN→FINALIZED via a status-guarded atomic UPDATE (RECON-01 + RECON-02).

settlement-service is currently consume-only (SettlementApplication.java:6 "No @EnableScheduling"; no Redisson, no HTTP client, no alert port). RESEARCH's single biggest trap is wiring these in without the Redisson-autoconfig-boots-against-Redis failure (Pitfall 1) — solved by cloning product's TestRedissonConfig mock. Every new piece is a verbatim clone of a shipped sibling-module file (CancelRestoreRedriveScheduler, PaymentQueryHttpClient/HttpClientConfig, OperationAlertPort/LogOperationAlertAdapter, TestRedissonConfig), and the reconcile logic is almost entirely COMPOSITION of Phase 1/2 primitives (SaleLedgerService/CancelLedgerService.record(), SettlementFeeCalculator.compute(), SettlementWeek, SettlementConfigService.getRate()).

Decisions (RESEARCH 4 open questions — all resolved in-plan, none left open):
- D-Q1 (cancel windowing): consume 03-01's contract as-is — record SALE only for payments whose created_at∈window, record every returned cancel (server pre-windowed by completed_at) with occurredAt=completedAt so record() buckets it into this header's week.
- D-Q2 (cadence + grace): SettlementReconcileScheduler @Scheduled(fixedDelay=3_600_000) (hourly poll, lock-guarded, re-runnable idempotently — no cron parsing); eligible = OPEN headers with period_end < today(KST) − grace-days, grace-days = @Value("${settlement.reconcile.grace-days:1}").
- D-Q3 (drift policy): ALERT-ONLY. Reconcile back-fills missing lines (the legitimate correction); recompute gross/cancel = Σlines and if they differ from the header columns, alert — do NOT silently rewrite the header gross/cancel. Finalize's fee/vat/net is computed from Σlines (authoritative).
- D-Q4 (finalize race): week-close grace window + status-guarded UPDATE (WHERE status='OPEN'), NOT SELECT FOR UPDATE. The FINALIZED guard in record() is the non-optional backstop.

Purpose: prove the whole reconcile→finalize architecture on the best early-context tokens — Redisson wiring, HTTP pull, back-fill dedup, Σlines authority, atomic finalize, immutability — so any dead-end surfaces after one commit.
Output: settlement build.gradle + application.yml + @EnableScheduling; OperationAlertPort/adapter; PaymentSettlementPort + HttpClient + HttpClientConfig; SettlementReconcileService + SettlementReconcileScheduler; new repo queries (finalizable select, Σlines-by-type, atomic finalize UPDATE); FINALIZED guard in the two ledger services; TestRedissonConfig; a Testcontainers reconcile IT.

INV note: all changes are inside settlement-service (its own DB/module) — the payment cancel core stays diff 0 (formally gated in 03-03). No settlement migration: fee/vat/net/finalized_at columns already exist (V1__create_settlement_core.sql:21-25).
</objective>
