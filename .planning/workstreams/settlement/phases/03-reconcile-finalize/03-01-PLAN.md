<objective>
Add payment-service's reconcile-only read API `GET /v1/payments/settlement?merchantId&from&to` (RECON-03): for one merchant and a KST-settlement-week window, return completed payments (SALE window by payment.created_at) with their in-window cancellations (CANCEL window by cancel_request.completed_at) so settlement-service can HTTP-pull the period and back-fill event-lost ledger lines. Read-only, new files only, no migration.

This is the ONLY payment-service change in Phase 3 and the single INV-01 allowlist delta (a `PaymentSettlement` token). It mirrors `PaymentExistsQueryService` (read-only use-case) and must NOT edit `PaymentController.java` or `PaymentJpaRepository.java` — both would break the one-token allowlist and collide with the parallel checkout-buynow session (RESEARCH Pitfall 6, anti-pattern "Editing PaymentController.java").

Decision (RESEARCH Open Q1 — cancel windowing, resolved here, not left open): SALE list = payments with `payment.created_at ∈ [from,to)` (status COMPLETED / PARTIAL_CANCELLED / CANCELLED — every non-PENDING is a real sale, PaymentStatus.java:11-15); CANCEL list = `cancel_request` rows with `status='COMPLETED'` AND `completed_at ∈ [from,to)`, windowed INDEPENDENTLY of the parent payment's week. The two are assembled into the prompt-locked nested shape `{paymentKey, merchantId, totalAmount, status, createdAt, cancels:[{cancelRequestId, cancelAmount, completedAt}]}` keyed by paymentKey: a payment appears if its created_at is in-window OR it owns ≥1 in-window cancel (a cross-week "carrier"). This keeps each line's occurred_at correct for SettlementWeek attribution on the settlement side (RESEARCH Pitfall 5).

Purpose: give the reconciler an authoritative, cross-DB-free source of truth for a week so event loss is recoverable.
Output: PaymentSettlementController + PaymentSettlementQueryService + PaymentSettlementJpaRepository + PaymentSettlementResponse, backed by a Testcontainers integration test proving window semantics + read-only.

Security: no caller authz by design (RESEARCH Security V4) — this endpoint exposes cross-merchant financials and is fenced only by deploy-time NetworkPolicy (gateway-pod-only ingress, same class as `infra/k8s/networkpolicy/product-ingress.yaml`). Record this as a deploy gate in the SUMMARY. Input validation (merchantId>0, from<to, max 60-day window) is enforced at the controller (ASVS V5).
</objective>

    PaymentSettlementQuery (application/usecase, mirror PaymentExistsQuery): a use-case interface `List<PaymentSettlementView> query(long merchantId, Instant from, Instant to)` where PaymentSettlementView is the application-layer projection (nest it or use the DTO record — keep the application layer free of Spring/web types). Prefer defining the returned shape as records here so the service stays hexagonal.

    PaymentSettlementJpaRepository (infrastructure/persistence, NEW @Repository extends JpaRepository<PaymentJpaEntity, Long>): two read queries over existing columns.
      (1) SALE window: `List<PaymentJpaEntity> findByMerchantIdAndCreatedAtGreaterThanEqualAndCreatedAtLessThan(long merchantId, LocalDateTime from, LocalDateTime to)` — payment.created_at ∈ [from,to). Include all statuses except PENDING (filter in the service via PaymentStatus, or a derived query with a status IN list). created_at is a UTC LocalDateTime (V1:16), so callers convert the from/to Instants to LocalDateTime at UTC.
      (2) CANCEL window: a native/JPQL projection joining cancel_request → payment for this merchant: `SELECT cr.id AS cancelRequestId, cr.cancel_amount AS cancelAmount, cr.completed_at AS completedAt, p.payment_key AS paymentKey, p.merchant_id AS merchantId, p.total_amount AS totalAmount, p.status AS status, p.created_at AS createdAt FROM cancel_request cr JOIN payment p ON cr.payment_id = p.id WHERE p.merchant_id = :merchantId AND cr.status = 'COMPLETED' AND cr.completed_at >= :from AND cr.completed_at < :to` — return a nested projection record (e.g. `CancelRow`) inside PaymentSettlementJpaRepository. This carries enough parent-payment fields to materialise a carrier payment whose created_at is out of window.

    PaymentSettlementQueryService (application/service, @Service, mirror PaymentExistsQueryService, read-only — @Transactional(readOnly = true)) implements PaymentSettlementQuery: run both repo queries, then ASSEMBLE the nested shape keyed by paymentKey. Build a LinkedHashMap<String, builder> seeded from the SALE list (each non-PENDING payment → an entry with its SALE fields and an empty cancels list). Then fold in every CancelRow: append {cancelRequestId, cancelAmount, completedAt} to its paymentKey's entry, CREATING a carrier entry (from the CancelRow's parent fields) if that paymentKey was not in the SALE window. Return the assembled list. Amounts stay BigDecimal, times as Instant (convert LocalDateTime→Instant at UTC). Do not mutate anything.

    PaymentSettlementResponse (presentation/dto, record): `{ String paymentKey, long merchantId, BigDecimal totalAmount, String status, Instant createdAt, List<Cancel> cancels }` with nested `record Cancel(long cancelRequestId, BigDecimal cancelAmount, Instant completedAt)`. Serialise createdAt/completedAt as ISO-8601 UTC (trailing Z) — settlement parses with Instant.parse. This is the wire contract the settlement HTTP client (03-02) mirrors byte-for-byte.

    PaymentSettlementController (presentation/controller, @RestController @RequestMapping("/v1/payments/settlement"), @GetMapping): params merchantId (long), from (String ISO-8601), to (String ISO-8601). VALIDATE first (ASVS V5): merchantId > 0, Instant.parse(from) < Instant.parse(to), and (to − from) ≤ 60 days — reject with 400 (throw IllegalArgumentException; the existing GlobalExceptionHandler / @RestControllerAdvice maps it, mirror the payment error style) BEFORE calling the service. Map the service views → List<PaymentSettlementResponse>. Class Javadoc: "no caller authz by design — deploy-time NetworkPolicy (gateway-pod-only ingress) fences cross-merchant reads, same class as product-ingress" (mirror SettlementQueryController). The literal path /v1/payments/settlement does not collide with PaymentController's /{paymentKey}/exists (Spring prefers the literal, more-specific mapping).
